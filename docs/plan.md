# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 BuildLog 기능을 어떤 순서로 개발하고 확인할지 설명합니다.

한 번에 하나의 Phase만 진행하고, 해당 Phase의 자동 테스트와 직접 확인이 모두 끝난 뒤 다음 Phase로 넘어갑니다.

## 2. 확정된 기술 구성

| 영역 | 기술 | 역할 |
| --- | --- | --- |
| 프런트엔드 | React, TypeScript | 사용자가 보는 화면과 입력 처리 |
| 백엔드 | Python, FastAPI | 회원, 권한, 기록과 커뮤니티 API |
| 데이터 접근 | SQLAlchemy | Supabase PostgreSQL과 SQLite3를 같은 코드로 사용 |
| 데이터 구조 변경 | Alembic | 테이블 변경 내역 생성과 적용 |
| 실제 서비스 데이터베이스 | Supabase PostgreSQL | 개발 연동과 실제 서비스 데이터 저장 |
| 자동 테스트 데이터베이스 | SQLite3 | 빠르고 독립적인 테스트 실행 |

Supabase는 첫 버전에서 데이터베이스로 사용합니다. Supabase Auth를 사용하지 않으며, 회원가입과 로그인은 `spec.md`의 규칙대로 FastAPI에서 처리합니다.

SQLite3는 자동 테스트용입니다. 각 테스트는 다른 테스트의 데이터에 영향을 받지 않게 별도의 임시 데이터베이스에서 실행합니다. 실제 서비스 데이터는 Supabase PostgreSQL에 저장합니다.

## 3. 개발 원칙

- `spec.md`에 없는 사용자 기능은 추가하지 않습니다.
- 프런트엔드와 백엔드는 HTTP API로 통신합니다.
- 화면 검사는 React와 FastAPI 양쪽에서 수행하되, 최종 권한 판단은 반드시 FastAPI가 합니다.
- 데이터 조회·수정·삭제 때마다 현재 로그인한 사용자의 권한을 확인합니다.
- 비밀번호 원문, Supabase 접속 정보와 로그인 비밀값은 코드에 적지 않습니다.
- 실제 비밀값은 `.env`에 두고, 필요한 설정 이름만 `.env.example`에 기록합니다.
- 데이터 구조는 Supabase PostgreSQL과 SQLite3에서 모두 동작하게 작성합니다.
- 각 Phase에서 정상 상황, 잘못된 입력, 실패 상황과 권한을 함께 테스트합니다.
- 실패한 테스트를 건너뛰지 않고 원인을 해결한 뒤 다음 Phase로 넘어갑니다.

## 4. 예정된 프로젝트 구조

```text
buildlog/
├─ backend/
│  ├─ app/
│  │  ├─ api/             # FastAPI 요청 경로
│  │  ├─ core/            # 설정, 보안, 공통 기능
│  │  ├─ db/              # 데이터베이스 연결과 세션
│  │  ├─ models/          # SQLAlchemy 데이터 구조
│  │  ├─ schemas/         # 요청과 응답의 입력 검사
│  │  ├─ services/        # 기능별 처리 규칙
│  │  └─ main.py          # FastAPI 시작점
│  ├─ alembic/            # 데이터 구조 변경 기록
│  ├─ tests/              # SQLite3 기반 백엔드 테스트
│  ├─ requirements.txt
│  └─ .env.example
├─ frontend/
│  ├─ src/
│  │  ├─ api/             # FastAPI 호출
│  │  ├─ components/      # 공통 화면 요소
│  │  ├─ pages/           # 기능별 화면
│  │  ├─ routes/          # 화면 이동과 로그인 보호
│  │  ├─ styles/          # 공통 스타일
│  │  └─ types/           # 화면에서 쓰는 데이터 타입
│  ├─ tests/
│  ├─ package.json
│  └─ .env.example
├─ database/
│  └─ README.md           # Supabase와 테스트 DB 사용 방법
└─ docs/
```

파일과 폴더의 세부 이름은 실제 생성 도구의 기본 구조에 맞게 조금 달라질 수 있지만, 역할 분리는 유지합니다.

## 5. 환경 설정 이름

실제 값은 개발 단계에서 `.env`에 넣습니다.

### 백엔드

- `DATABASE_URL`: Supabase PostgreSQL 연결 주소
- `TEST_DATABASE_URL`: SQLite3 테스트 주소. 기본값은 테스트 전용 임시 DB
- `AUTH_SECRET_KEY`: 로그인 정보를 안전하게 확인하기 위한 비밀값
- `FRONTEND_ORIGIN`: React 화면 주소
- `ENVIRONMENT`: 개발, 테스트 또는 운영 환경 구분

### 프런트엔드

- `VITE_API_BASE_URL`: FastAPI 서버 주소

비밀값은 채팅이나 문서에 적지 않습니다. `.env.example`에는 예시 형식만 기록합니다.

## Phase 0. 개발 기준과 환경 확인

### 목표

코드를 만들기 전에 문서와 기술 기준을 맞추고, Phase 1을 시작할 준비가 되었는지 확인합니다.

### 작업

1. `MVP.md`, `PRD.md`, `spec.md`, `plan.md`의 기능 범위를 비교합니다.
2. 포함 기능과 제외 기능이 서로 충돌하지 않는지 확인합니다.
3. FastAPI, React, Supabase PostgreSQL, SQLite3 테스트 구조가 모든 문서에서 일치하는지 확인합니다.
4. Python, Node.js와 패키지 관리 도구의 설치 상태를 확인합니다.
5. Supabase 연결 없이도 SQLite3 테스트로 Phase 2~12를 진행할 수 있는지 확인합니다.
6. 환경 변수 이름과 `.env.example` 작성 기준을 확정합니다.
7. 화면 목록, API 영역과 데이터 모델 목록을 개발 체크리스트로 정리합니다.
8. 기존 폴더와 사용자 파일을 보존할 범위를 확인합니다.

### 예상 변경 파일

- `docs/PRD.md`
- `docs/spec.md`
- `docs/plan.md`
- 필요한 경우 `docs/phase0-checklist.md`

### 확인 방법

- 문서에 Django, Django 템플릿이나 Django 관리자 전제가 남아 있지 않은지 검색합니다.
- 실제 서비스 DB가 Supabase PostgreSQL, 테스트 DB가 SQLite3로 구분되어 있는지 확인합니다.
- 첫 버전 기능과 제외 기능 목록이 문서 사이에서 일치하는지 확인합니다.
- 아직 패키지 설치나 데이터베이스 변경을 하지 않았는지 확인합니다.

### 완료 조건

- Phase 1에서 만들 구조와 필요한 도구가 분명합니다.
- 사용자에게 받아야 할 값과 나중에 필요한 값을 구분해 설명할 수 있습니다.
- 해결되지 않은 문서 충돌이 없습니다.

## Phase 1. FastAPI·React 프로젝트 뼈대 만들기

### 목표

기능이 없어도 FastAPI와 React가 각각 실행되고 React에서 FastAPI의 응답을 확인할 수 있게 합니다.

### 작업

1. `backend`에 Python 가상환경과 FastAPI 프로젝트를 준비합니다.
2. FastAPI, 실행 서버, 설정 관리, SQLAlchemy, Alembic과 테스트 도구 버전을 기록합니다.
3. FastAPI 상태 확인 API를 만듭니다.
4. `frontend`에 React와 TypeScript 프로젝트를 준비합니다.
5. React의 기본 화면과 화면 이동 기반을 만듭니다.
6. React에서 FastAPI 상태 확인 API를 호출해 결과를 표시합니다.
7. 개발용 React 주소만 FastAPI 호출을 허용하도록 설정합니다.
8. 백엔드와 프런트엔드 `.env.example`을 만듭니다.
9. 테스트용 SQLite3 파일과 생성 파일이 Git 기록 대상에서 제외되도록 확인합니다.

### 주요 결과물

- `backend/app/main.py`
- `backend/app/core/config.py`
- `backend/requirements.txt`
- `backend/.env.example`
- `frontend/src/`
- `frontend/package.json`
- `frontend/.env.example`

### 확인 방법

- FastAPI 서버가 오류 없이 시작되는지 확인합니다.
- FastAPI 자동 API 문서와 상태 확인 API가 열리는지 확인합니다.
- React 개발 서버가 오류 없이 시작되는지 확인합니다.
- React 화면에서 FastAPI 응답이 보이는지 확인합니다.
- 실제 비밀값이 코드나 예시 파일에 들어가지 않았는지 확인합니다.

### 완료 조건

- React와 FastAPI가 독립적으로 실행되고 API 통신까지 성공합니다.
- 아직 회원이나 기록 기능은 만들지 않습니다.

## Phase 2. 사용자 모델과 데이터베이스 기반 만들기

### 목표

Supabase PostgreSQL과 SQLite3 테스트에서 함께 사용할 데이터 접근 구조와 사용자 모델을 만듭니다.

### 작업

1. SQLAlchemy 데이터베이스 연결과 요청별 세션 관리를 만듭니다.
2. 실행 환경에 따라 `DATABASE_URL` 또는 테스트 DB를 선택하게 합니다.
3. Alembic 초기 설정을 만들고 SQLAlchemy 모델 정보를 연결합니다.
4. 사용자 모델에 이메일, 비밀번호 해시, 닉네임, 운영자 여부와 날짜 정보를 둡니다.
5. 이메일과 닉네임에 중복 방지 조건을 둡니다.
6. 비밀번호 원문을 저장하지 않고 안전한 해시만 저장합니다.
7. 첫 Alembic 변경 파일을 만듭니다.
8. SQLite3 임시 DB에 테이블을 만들고 사용자 모델 테스트를 실행합니다.
9. PostgreSQL과 SQLite3에서 다르게 동작하는 전용 기능에 의존하지 않는지 확인합니다.

### 확인 방법

- SQLite3 테스트 DB에 사용자 생성과 조회가 되는지 확인합니다.
- 중복 이메일과 닉네임이 데이터베이스에서도 거절되는지 확인합니다.
- 비밀번호 원문이 저장되지 않는지 확인합니다.
- 각 테스트가 서로 데이터를 공유하지 않는지 확인합니다.
- Alembic 변경 파일을 빈 DB에 적용하고 되돌릴 수 있는지 확인합니다.

### 완료 조건

- SQLite3 기반 자동 테스트가 통과합니다.
- 같은 모델을 Supabase PostgreSQL에 적용할 준비가 되어 있습니다.

## Phase 3. 회원가입·로그인·닉네임 변경

### 목표

React 화면과 FastAPI API를 연결해 회원가입, 로그인, 로그아웃과 닉네임 변경을 완성합니다.

### 작업

1. 회원가입 요청·응답 입력 규칙을 만듭니다.
2. 이메일, 비밀번호와 닉네임 조건을 FastAPI에서 검사합니다.
3. 로그인 API와 안전한 로그인 유지 방식을 만듭니다.
4. 로그아웃과 현재 로그인 사용자 확인 API를 만듭니다.
5. 닉네임 변경 API를 만듭니다.
6. 로그인한 사용자만 이용할 수 있는 공통 권한 확인을 만듭니다.
7. React 회원가입, 로그인과 계정 설정 화면을 만듭니다.
8. React의 개인 화면을 로그인한 사용자만 열 수 있게 합니다.
9. 실패 시 정해진 입력값을 유지하고 입력칸 아래에 이유를 보여줍니다.
10. SQLite3로 회원 기능 API와 화면 흐름을 테스트합니다.

### 확인 방법

- 입력 길이의 최소, 최대와 초과 값을 검사합니다.
- 중복 이메일과 닉네임이 거절되는지 확인합니다.
- 로그인 성공·실패와 로그아웃을 확인합니다.
- 로그인하지 않은 사용자가 개인 API와 화면에 접근하지 못하는지 확인합니다.
- 사용자가 자신의 닉네임만 변경할 수 있는지 확인합니다.

### 완료 조건

- `spec.md` 회원 기능의 모든 확인 항목이 통과합니다.
- 이메일 확인과 비밀번호 찾기는 만들지 않습니다.

## Phase 4. 공부 기록·할 일·오류 기록 데이터 구조

### 목표

세 종류 기록의 SQLAlchemy 모델, 요청·응답 구조와 Alembic 변경 파일을 만듭니다.

### 작업

1. 공부 기록 모델을 만듭니다.
   - 작성자, 제목, 내용, 공개 여부
   - 작성·수정 날짜와 시간
2. 할 일 모델을 만듭니다.
   - 작성자, 제목, 완료 여부, 공개 여부
   - 작성·수정·완료 날짜와 시간
3. 오류 기록 모델을 만듭니다.
   - 작성자, 오류 제목, 오류 내용, 해결 방법, 해결 여부, 공개 여부
   - 작성·수정·해결 날짜와 시간
4. 새 기록은 비공개, 새 할 일은 미완료, 새 오류는 미해결을 기본값으로 둡니다.
5. 작성자와 각 기록을 연결합니다.
6. 입력 길이와 상태 전환 규칙을 요청 구조와 서비스 계층에 둡니다.
7. Alembic 변경 파일을 만듭니다.
8. SQLite3에서 모델, 기본값과 상태 전환을 테스트합니다.

### 확인 방법

- 세 기록을 SQLite3에 저장하고 다시 읽을 수 있는지 확인합니다.
- 기본 공개·완료·해결 상태가 맞는지 확인합니다.
- 완료·해결 날짜가 상태 변화에 맞게 저장·삭제되는지 확인합니다.

## 7. 실제 진행 방법

1. 한 번에 Phase 하나만 진행합니다.
2. Phase를 시작하기 전에 사용자에게 필요한 값이나 설정을 먼저 알립니다.
3. 비밀값은 채팅으로 받지 않고 사용자가 로컬 `.env` 또는 배포 서비스 설정에 넣게 합니다.

5. 완료 기준을 통과한 뒤 다음 Phase로 넘어갑니다.

## 8. 사용자 준비가 필요한 시점

### Phase 0

사용자가 제공할 값은 없습니다. 설치 상태와 문서를 확인하기만 합니다.

### Phase 1

Python 또는 Node.js가 없다면 설치가 필요할 수 있습니다. 먼저 현재 설치 상태를 확인한 뒤 필요한 것만 안내합니다.

### Phase 13

Supabase 프로젝트와 PostgreSQL 연결 정보가 필요합니다. 비밀번호나 전체 연결 주소는 채팅에 보내지 않고 로컬 `.env`에 직접 넣습니다.

### Phase 14

선택한 배포 서비스 계정이 필요합니다. 별도 도메인을 사용할 경우 도메인 설정도 이 단계에서 진행합니다.
